# jev-2048 設計書

- 日付: 2026-09-21
- ステータス: レビュー待ち

## 目的

TypeSafe AI の System One モデル「jev」(生成せず、型付きの判定だけを数百 ms で返すモデル)に 2048 を遊ばせ、次の問いに答える PoC を作る。

1. 反射だけで動く AI は 2048 でどこまで戦えるか(古典 AI との成績比較)
2. 同じモデルでも「盤面の聞き方」で強さはどれだけ変わるか(jev-raw と jev-sim の比較)

加えて、jev が 1 手ずつ打つ様子を確率分布・confidence 付きでターミナルから観戦できるようにする。

## スコープ外

- jev を Score で評価関数として使うプレイヤー(案 C)。API 呼び出しが膨らむため今回は入れない
- 人間がプレイするモード
- TUI フレームワーク(Bubble Tea 等)の導入。観戦は入力を受けない再描画だけなので ANSI エスケープで足りる
- Web UI、結果の可視化グラフ

## 前提となる jev API 仕様

- `POST https://api.typesafe.ai/v1/systemone`
- ヘッダ: `Authorization: Bearer <API_KEY>`, `Content-Type: application/json`
- リクエスト: `state`(文字列・オブジェクト・配列)、`model`(`"jev-latest"`)、`questions`(キー → 質問のマップ)
- Choice 質問: `type: "choice"`, `instructions`, `criteria`(選択肢名 → 説明のマップ、最大 255 個)
- Choice 応答: `choice`(最大確率の選択肢)、`probabilities`(全選択肢の分布、合計 1)、`confidence`(0〜1)
- レスポンス全体: `model`, `answers`, `usage`(`input_tokens`, `output_tokens`)
- エラー: 401(キー不正)、422(バリデーション)、429(レート制限)、529(過負荷)。429/529 は指数バックオフで再試行
- 料金とレート制限の具体値はドキュメントに記載がなく未確認

実装の最初に API を 1 回叩き、実際の応答形とレイテンシがこの前提と一致するかを確認する。ずれがあればこの節を更新してから先へ進む。

## 構成

言語は Go。依存は標準ライブラリのみ。モジュール名は `github.com/tatsuo48/jev-poc`。

```
cmd/jev2048/main.go   CLI エントリ(watch / bench サブコマンド)
internal/game/        盤面とルール
internal/player/      プレイヤーのインターフェースと各実装
internal/jev/         jev HTTP クライアント
internal/watch/       観戦用の ANSI 描画
internal/bench/       ベンチマーク実行と集計
```

### game

4×4 の盤面とルールを純粋関数で持つ。乱数以外の状態を持たない。

- `Board`: `[4][4]int`(タイルの値そのもの。空きは 0)
- `Move`: `Up / Down / Left / Right`
- `Slide(b Board, m Move) (next Board, gained int, moved bool)`: スライドとマージ。1 回の移動で同じタイルは 1 度しかマージしない(`[2,2,2,2]` → `[4,4,0,0]`)
- `LegalMoves(b Board) []Move`: 盤面が変化する手だけを返す
- `Spawn(b Board, r *rand.Rand) Board`: 空きマスに 90% で 2、10% で 4 を置く
- `Game`: 盤面、スコア、手数、シード付き `*rand.Rand` を持ち、`Step(m Move)` で 1 手進める。合法手が無くなったら終了

同じシードなら、同じ手の列に対して必ず同じ盤面列になる。

### player

```go
type Player interface {
    Name() string
    Pick(ctx context.Context, b game.Board) (game.Move, Info, error)
}

type Info struct {
    Probabilities map[game.Move]float64 // jev 以外は nil
    Confidence    float64               // jev 以外は 0
    Latency       time.Duration
    InputTokens   int
    OutputTokens  int
}
```

実装は 5 つ。

| 名前 | 内容 |
|---|---|
| `random` | 合法手から一様ランダム。乱数はシード付き |
| `greedy` | 1 手で得られるスコアが最大の手。同点なら空きマスが多い方 |
| `expectimax` | 深さ 3 の expectimax。評価関数は空きマス数・単調性・最大タイルが角にあるかの重み付き和 |
| `jev-raw` | 盤面の数字だけを `state` に渡し、合法手から Choice で選ばせる |
| `jev-sim` | 各合法手を打った後の盤面と特徴量を `state` に渡し、合法手から Choice で選ばせる |

jev 系の共通ルール:

- `criteria` には合法手だけを入れる。したがって jev が不正な手を返すことはない
- 合法手が 1 つだけのときは API を呼ばずその手を返す
- 応答の `choice` をそのまま採用する。`probabilities` と `confidence` は `Info` に入れる
- `jev.Client` には直接依存せず、`Ask` メソッドだけを持つインターフェース(`player.Asker`)越しに呼ぶ。テストではここに偽物を差し込む

`jev-raw` の `state`:

```json
{"board": [[2,0,0,4],[0,8,0,0],[0,0,16,0],[2,0,0,0]], "score": 120}
```

`jev-sim` の `state`:

```json
{
  "board": [[...]],
  "candidates": {
    "left":  {"board": [[...]], "gained": 8, "empty_cells": 9, "merges": 2, "max_tile": 64, "max_in_corner": true},
    "up":    {"board": [[...]], "gained": 0, "empty_cells": 8, "merges": 0, "max_tile": 64, "max_in_corner": false}
  }
}
```

`instructions` は両者とも「2048 で長期的に最も高いスコアに繋がる手を選べ」という趣旨の固定文。`criteria` の説明は `jev-raw` では方向の意味、`jev-sim` では「`candidates` の同名キーを参照」とする。

### jev

- `Client` は `Ask(ctx, state any, questions map[string]Question) (Response, error)` を持つ
- API キーは環境変数 `TYPESAFE_API_KEY` から読む。未設定なら起動時にエラーで止める。キーはログにも出力にも出さない
- エンドポイントは `JEV_ENDPOINT` で上書き可能(テストとプロキシ用)
- 429 と 529 は指数バックオフ(初回 500ms、倍々、最大 5 回)で再試行。401 と 422 は即エラー
- HTTP タイムアウトは 1 リクエスト 10 秒
- 呼び出し回数と `usage` のトークン数を積算し、`--max-calls` を超えたら `ErrBudgetExceeded` を返す

### watch

`jev2048 watch --player jev-sim --seed 42 [--delay 100ms]`

1 手ごとに画面を再描画する。表示するのは、盤面(タイルの値で色分け)、スコア、手数、直前の手、合法手ごとの確率バー、confidence、レイテンシ、累積トークン数。jev 以外のプレイヤーでは確率バーと confidence を表示しない。

### bench

`jev2048 bench --players random,greedy,expectimax,jev-raw,jev-sim --games 5 --seed 1 [--max-calls 20000] [--out results.jsonl]`

- シードは `seed, seed+1, …, seed+games-1`。全プレイヤーが同じシード集合で遊ぶ
- ゲーム単位で並列実行する(既定の並列数 4)。jev のレイテンシが支配的なため
- 終了時に表を出す: プレイヤーごとの平均スコア、最高スコア、最大タイルの分布、平均手数、平均レイテンシ、総トークン数、エラーで中断したゲーム数
- `--out` 指定時は 1 手 1 行の JSONL を書く: プレイヤー、シード、手数、盤面、選んだ手、確率分布、confidence、レイテンシ

## エラー処理

- jev API が再試行しても失敗した場合、そのゲームは「エラーで中断」として記録し、集計の平均からは除外して件数を別に表示する。ランダム手での穴埋めはしない(成績が汚れるため)
- `ErrBudgetExceeded` のときは実行中のゲームをすべて中断し、そこまでの結果を出力して非ゼロで終了する
- `watch` では API エラーを画面に表示して終了する
- Ctrl-C で `context` をキャンセルし、`bench` はそこまでの結果を出力する

## テスト

- `game`: `Slide` のテーブルテスト(4 方向、連続マージしないこと、動かない手の `moved=false`)、`LegalMoves`、同一シードでの決定性、ゲーム終了判定
- `player`: `greedy` と `expectimax` は固定盤面で期待する手を確認。jev 系は偽の `jev.Client` を差し込み、`state` と `criteria` の組み立て(合法手だけが入ること)、合法手 1 つのとき API を呼ばないことを確認
- `jev`: `httptest` でリクエストの形、認証ヘッダ、429 → 成功の再試行、401 の即エラー、`--max-calls` の上限を確認
- `bench`: 偽プレイヤーで集計値と、エラー中断ゲームの扱いを確認
- 実 API を叩くテストは `TYPESAFE_API_KEY` があるときだけ走る統合テスト 1 本にとどめる

## 実装の順序

1. API を 1 回叩いて応答形とレイテンシを確認(前提の節を検証)
2. `game`
3. `player` の古典 3 種と `bench`
4. `jev` クライアントと `jev-raw` / `jev-sim`
5. `watch`
6. 全プレイヤーで bench を回し、結果を README にまとめる
